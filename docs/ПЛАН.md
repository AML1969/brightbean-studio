## 1. Локальная среда на вашей машине — 0,5 дня
Цель: приложение открывается на http://localhost:8000, воркер публикует, вы входите под админом.

1. Установить Docker Desktop (Windows/macOS) или docker + compose (Linux).
2. `git clone https://github.com/AML1969/brightbean-studio.git && cd brightbean-studio`
3. `cp .env.example .env`, сгенерировать и вписать `SECRET_KEY`, `ENCRYPTION_KEY_SALT`.
   ENCRYPTION_KEY_SALT после первого подключения соцсети менять нельзя: все токены станут нечитаемыми.
4. `docker compose up -d --build`, затем `docker compose exec app python manage.py createsuperuser`.
5. Войти, принять Terms, создать тестовый пост в «Drafts». Проверить `docker compose logs -f worker`.
6. Для OAuth с localhost поставить cloudflared: `cloudflared tunnel --url http://localhost:8000`,
   полученный https-адрес вписать в `APP_URL` и `CSRF_TRUSTED_ORIGINS`, перезапустить `app`.

Готово, когда: пост со статусом scheduled на ближайшую минуту уходит в «Sent» на Bluesky или Mastodon (этап 3a).

## 2. Безопасный выход в интернет (VPS) — 1–2 дня
Нужен, потому что Meta, TikTok и Google требуют публичный HTTPS для callback и вебхуков, а аудиты приложений проводятся на живом адресе.

1. VPS 2 vCPU / 4 ГБ (образ ~100 МБ RAM на процесс + Postgres + воркер), домен, A-запись.
2. Исправить production-compose перед первым `up` (всё подтверждено в анализе):
   - убрать `ports: 5432:5432` у postgres или привязать к `127.0.0.1`;
   - задать сильный пароль Postgres и единый `DATABASE_URL` для migrate/app/worker (сейчас migrate хардкодит `postgres:postgres`);
   - прокинуть `APP_DOMAIN` в сервис caddy, иначе Caddy обслуживает только localhost;
   - в `.env`: `DEBUG=false` (иначе отключается rate limiting), `ALLOWED_HOSTS`, `APP_URL=https://…`;
   - добавить сервис `redis` и `REDIS_URL`: без него лимиты и антибрутфорс живут в памяти каждого из 4 gunicorn-воркеров.
3. SMTP: Яндекс 360 / Resend / Mailgun; заполнить `EMAIL_*`, `DEFAULT_FROM_EMAIL`. Без этого приглашения и сброс пароля падают.
4. `SIGNUP_MODE=invite` или `closed`: установка с `open` открыта для регистрации всему интернету.
5. Бэкапы: cron с `pg_dump` в объектное хранилище и копия volume `media_data`; проверить восстановление один раз.
6. `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d`; проверить `/health/`.

Готово, когда: сайт открывается по https, логин работает, письмо-приглашение доходит, бэкап восстанавливается.

## 4. Закрыть подтверждённые дефекты перед приглашением других людей — 2–3 дня
Пока в системе один пользователь, эти пункты не критичны. Перед командой или клиентами в портале:
1. `post_delete`: проверка автора или права `edit_others_posts` (`apps/composer/views.py:2498`).
2. `transition_platform_post`: разрешать только переходы, на которые есть право (`views.py:1294`).
3. `schedule`/`add_to_queue`/CSV-импорт: те же проверки режима согласования и `publish_directly`, что у `publish_now`.
4. Переименование пространства только для owner/manager (`apps/workspaces/views.py:107`).
5. Зарегистрировать `generate_recurring_posts` как повторяющуюся задачу, иначе повторяющиеся посты не создаются.
6. Очистка `PostInsightsSnapshot` старше 180 дней и запись сырого JSON один раз на пост, а не на метрику.
7. Тесты на каждый пункт, затем PR в upstream: это улучшает ваш форк и уменьшает будущие конфликты.

## 5. Провайдер Telegram — 4–6 дней
Цель: публикация текста, фото, видео и альбомов в каналы и группы через Bot API.

Дизайн:
- `providers/telegram.py` наследует `SocialProvider`; `auth_type = SESSION` (как Bluesky): пользователь вводит токен бота и `@username` или id канала, бот должен быть админом канала. Проверка через `getChat` + `getChatMember`.
- Типы: TEXT (4096), IMAGE/VIDEO с подписью (1024), CAROUSEL через `sendMediaGroup` (до 10). `needs_local_media = True` (Bot API принимает multipart, публичный URL не нужен, что удобно для локального запуска).
- Комментарии: через связанную группу обсуждений (`sendMessage` с `reply_to_message_id`), можно отложить.
- Аналитика: Bot API не отдаёт просмотры постов; поле «нет аналитики» (как у Bluesky), добавить в `NO_ANALYTICS_PLATFORMS`.
- Файлы (по замеру DEV.to): провайдер + реестр, enum `PlatformCredential.Platform` + 2 миграции (`credentials`, `social_accounts`), `PLATFORM_CHAR_LIMITS`/`PLATFORM_FIELD_CONFIG`/иконка, `apps/api/limits.PLATFORM_DAILY_POST_LIMIT`, форма подключения по образцу Bluesky, 4 шаблона, тесты по образцу `tests/providers/test_bluesky.py`.
- Вне плана: авторизация от имени пользователя (MTProto) и пересылка в личные чаты.

Готово, когда: пост с фото уходит в тестовый канал из календаря, ошибка «бот не админ» показывается в UI, тесты провайдера зелёные.

## 6. Русификация интерфейса — 6–10 дней, после этапов 4–5
Сейчас в проекте ноль `gettext`. Делать до стабилизации не стоит: каждый merge из upstream будет конфликтовать по шаблонам.
1. `LocaleMiddleware`, `LOCALE_PATHS`, `LANGUAGES = [ru, en]`, выбор языка в настройках аккаунта.
2. Обернуть строки: ~250 шаблонов (`{% trans %}`/`{% blocktrans %}`), ~90 вызовов `messages.*`, тексты писем, тексты ошибок провайдеров в `apps/social_accounts/error_messages.py`.
3. `makemessages -l ru`, перевод, `compilemessages` в Dockerfile.
4. Форматы дат и часовой пояс рабочего пространства по умолчанию Europe/Moscow.
5. Идти по экранам в порядке частоты использования: календарь → композер → inbox → настройки → письма.
Альтернатива дешевле: переводить только видимые пользователю экраны, оставив админку и API на английском.

## 7. Сопровождение форка — постоянно, ~0,5 дня в месяц
- `git fetch upstream && git merge upstream/main` раз в 1–2 недели; свои изменения держать небольшими и предлагать в upstream.
- Включить GitHub Actions в своём репозитории: CI из upstream заработает как есть (нужен только Postgres 16 на runner, он там предустановлен).
- Обновить Django до 5.2 LTS (5.1 без security-патчей), добавить lock-файл (`uv pip compile`) и Dependabot.
- Выровнять Python 3.12 в Dockerfile/CI с 3.13 в `.python-version`.

## Решения, которые нужны от вас
1. **Один пользователь или команда/клиенты?** Определяет срочность этапа 4 и `SIGNUP_MODE`.
2. **Telegram: только каналы через бота** (быстро) или нужна публикация от имени личного аккаунта (MTProto, отдельная большая задача)?
3. **Глубина русификации**: весь интерфейс, или только пользовательские экраны.
4. **Хранилище медиа**: локальный volume на VPS или S3-совместимое (Cloudflare R2 бесплатен до 10 ГБ). Менять потом неудобно.
5. **Видимость репозитория**: сейчас public. Для AGPL это нормально, но при хранении своих конфигов лучше private.

## Чего не будет
- Intelligence (ИИ-подсказки): закрытый облачный сервис авторов, в self-hosted недоступен.
- White-label по пространствам: в README заявлен, в коде не реализован; делать только при реальной потребности.
- Heroku/Render/Railway: оставляем Docker Compose на VPS как единственный целевой деплой.

## Риски плана
- Проверки Meta/TikTok/Google могут занять больше месяца и потребовать политику конфиденциальности и видео; начинать нужно в первый день.
- Единственный мейнтейнер upstream: при его паузе обновления прекратятся, форк должен быть самодостаточным.
- AGPL-3.0: если клиенты будут пользоваться вашей изменённой версией по сети (клиентский портал), вы обязаны предоставить им исходный код изменений.
