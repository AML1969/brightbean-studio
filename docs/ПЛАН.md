## Этап 0. Секреты и репозиторий — 0,5 дня, до первого подключённого аккаунта
1. Сгенерировать `SECRET_KEY` и `ENCRYPTION_KEY_SALT`: `python3 -c "import secrets;print(secrets.token_urlsafe(48))"` дважды. Положить в менеджер паролей с пометкой «никогда не менять на инстансе с подключёнными аккаунтами». Ключ шифрования токенов выводится из этой пары (`apps/common/encryption.py:22-30`), процедуры перешифрования в проекте нет.
   Ловушка: плейсхолдер `change-me-to-a-random-string` из `.env.example` проходит проверку `if not salt` как валидная соль. Забытый плейсхолдер молча зашифрует все токены общеизвестной солью, и потом её нельзя будет сменить без потери подключений.
2. `.env` никогда не коммитить и не вставлять в чат с Claude Code; при необходимости показывать только имена переменных. `.env` входит в бэкап-комплект: без него дамп базы не позволит восстановить подключения.
3. В GitHub: включить branch protection на `main` (только через PR с зелёным CI). CI из upstream уже работает в вашем репозитории.
4. Решение по AGPL-3.0 записать в README: лицензию и авторство сохранять; если клиенты будут пользоваться вашей изменённой версией по сети (клиентский портал `/portal/`), они вправе получить исходники изменений. Публичный репозиторий закрывает это требование автоматически.

## Этап 1. Локальный запуск в Docker Compose и дымовой тест — 0,5–1 день
Цель: приложение и воркер работают на вашей машине, пост реально уходит в сеть без единого developer-ключа.
1. Docker Desktop (Windows/macOS) или docker + compose plugin (Linux). Windows: `git config --global core.autocrlf false` до клонирования, иначе bind-mount `.:/app` принесёт CRLF в скрипты.
2. `git clone https://github.com/AML1969/brightbean-studio.git && cd brightbean-studio && cp .env.example .env`, вписать два секрета из этапа 0. `DATABASE_URL` не трогать: `docker-compose.override.yml` сам подставляет адрес сервиса postgres (README в этом месте устарел).
3. `docker compose up -d --build`. Первые 1–2 минуты страницы без стилей: CSS собирает сервис `tailwind`, следить `docker compose logs -f tailwind`.
4. `docker compose exec app python manage.py createsuperuser` (только email и пароль). Войти, принять Terms, попасть в «My Workspace».
5. Проверить, что воркер получил задачи: в админке `/admin/background_task/task/` должны быть строки `run_publish_cycle`, `confirm_pending_publishes`, `run_inbox_sync_cycle`, `sync_all_account_analytics`. Их создаёт сервис `migrate` через post_migrate; если их нет, воркер пуст и посты вечно висят в scheduled.
6. Дымовой тест: Connect → Bluesky (app password) или Mastodon (адрес инстанса). Пост с картинкой на +2 минуты → статус Published → строка в `PublishLog`.
7. Скрыть ненужные сети (LinkedIn, Pinterest, Threads, Google Business, DEV.to) через админку `Social accounts → Platform visibility`, не трогая код: ноль конфликтов с upstream.
Готово, когда: пост с картинкой опубликован воркером из контейнера; `/health/` отвечает 200; `docker compose logs worker` без ошибок.

## Этап 2. Цикл разработки и постоянный HTTPS-адрес — 1 день
1. Тесты внутри контейнера: `docker compose exec -e DJANGO_SETTINGS_MODULE=config.settings.test -e DB_HOST=postgres app pytest -q`. Тестовые настройки жёстко требуют PostgreSQL и читают хост из `DB_HOST` (по умолчанию localhost, внутри контейнера это неверно).
2. Статические проверки: `docker compose exec app make check` (ruff, mypy, makemigrations --check, как в CI). `pre-commit install` на хосте; поднять пины в `.pre-commit-config.yaml` (ruff v0.8.4 → 0.15.9) до версий CI.
3. Тестовый PR в свой репозиторий: убедиться, что все 5 джобов CI зелёные. Дальше работать только через ветки и PR.
4. Купить домен (нужен для VPS, redirect URI и страницы Privacy Policy). Поднять **именованный** туннель cloudflared `dev.ваш-домен → localhost:8000`. Быстрый `cloudflared tunnel --url` даёт случайный адрес при каждом запуске и ломает все redirect URI в кабинетах.
5. В `.env`: `APP_URL=https://dev.ваш-домен`, `CSRF_TRUSTED_ORIGINS=https://dev.ваш-домен`, **`SIGNUP_MODE=closed`** (dev-инстанс за туннелем — публичный сайт с DEBUG=True и открытой регистрацией; закрыть её, пока туннель живёт). `docker compose restart app worker`.
6. Проверить, что `https://dev.ваш-домен/media/media_library/...` открывается снаружи: Facebook, Instagram и Threads не загружают файл, а отдают Meta ссылку, собранную из `APP_URL` (`apps/publisher/engine.py:783-804`).
Готово, когда: pytest зелёный в контейнере, `make check` чистый, CI зелёный на PR, по https-адресу туннеля работает логин и отдаётся медиа.

## Этап 5. Провайдер Telegram — 5 дней, параллельно ожиданию проверок
Цель: из календаря публикуются текст, фото, видео и альбомы в каналы и группы, где бот администратор.

Архитектурные решения, принять до кода:
- **Как chat_id попадает в провайдер.** Сигнатуры `get_profile(access_token)` и `publish_post(access_token, content)` не получают аккаунт; per-account данные доезжают только через ветки по платформам в `_resolve_publish_credentials` (`apps/publisher/engine.py:64-111`: Mastodon `instance_url`, Bluesky `pds_url`, Facebook `page_id`). Варианты: (а) добавить ветку `telegram` в движок с `chat_id = account.account_platform_id` плюс тест; (б) хранить `bot_token|chat_id` внутри access_token. Рекомендация: (а), это явно и повторяет Facebook.
- `auth_type = SESSION` (как DEV.to, `providers/devto.py`): платформа считается «настроенной» без app-ключей. `account_platform_id = chat_id`, `instance_url` не использовать (это URLField).
- `needs_local_media = True`: Bot API принимает multipart; лимиты при загрузке 10 МБ фото / 50 МБ видео против 5/20 МБ при отправке по URL. Передавать свой timeout (базовый 30 с, `providers/base.py:35`) — 50 МБ за 30 с не уйдут, а ложный таймаут даст дубль, Bot API не идемпотентен.
- Без `parse_mode`: иначе неэкранированные символы в тексте пользователя дадут 400 «can't parse entities».
- Подпись к медиа 1024 символа против 4096 у текста, а `PLATFORM_CHAR_LIMITS` одно число на платформу: решить заранее (медиа + отдельное текстовое сообщение, или `PublishError(retryable=False)`).
- `refresh_token` не нужен: health-check обновляет токен только при непустом `oauth_refresh_token`.
- Аналитики нет (Bot API не отдаёт просмотры): `NO_ANALYTICS_PLATFORMS['telegram']` и `BACKFILL_DAYS_PER_PLATFORM['telegram'] = 0` (`apps/analytics/constants.py:11` требует оба).
- `platform_post_id = f"{chat_id}:{message_id}"`, `url = https://t.me/<username>/<message_id>` для публичных каналов.

Точки касания (по коммиту DEV.to `e4da3a2`: 16 файлов, 2 миграции):
`providers/telegram.py`, `providers/__init__.py`; `PlatformCredential.Platform` (`apps/credentials/models.py:43-56`) + миграция по образцу `credentials/0005_add_devto_platform.py`; миграция `social_accounts` по образцу `0012` (AlterField у трёх моделей: SocialAccount, PlatformVisibility, AnalyticsPlatformConfig) + get_or_create строки как в `0017`; `SocialAccount.PLATFORM_CHAR_LIMITS/PLATFORM_FIELD_CONFIG/platform_icon` (`apps/social_accounts/models.py:387-563`); `apps/api/limits.py PLATFORM_DAILY_POST_LIMIT`; `apps/common/context_processors.py:160-172`; view `connect_telegram` по образцу `connect_devto` (`apps/social_accounts/views.py:615-658`) + URL + ветки в `connect_platform` и `reconnect`; шаблон `telegram_connect.html`; иконка в двух партиалах `_platform_icon.html`, `connect.html`, `compose.html`; ветка в `engine.py` (см. выше).

Тесты: `tests/providers/test_telegram.py` по образцу `test_bluesky.py` с httpx mock (текст, фото, альбом, caption > 1024, 429 с `parameters.retry_after`, «бот не админ»); **обязательно** добавить `telegram` в жёсткий набор `tests/providers/test_base.py:17-31`, иначе тест реестра упадёт; тест connect-view.

По дням: 1 — провайдер и методы; 2 — реестр, enum, миграции, ветка движка; 3 — UI подключения и иконки; 4 — тесты, полный pytest, ruff, mypy, makemigrations --check; 5 — ручная проверка на реальном канале, раздел в `docs/ЗАПУСК.md` про BotFather.
Вне первой версии: комментарии через группу обсуждений, inbox, видео больше 50 МБ (нужен свой Bot API server), публикация от личного аккаунта (MTProto).
Готово, когда: пост с фото и альбом из 3 фото ушли в тестовый канал через воркер; ошибка прав бота показана в UI; тесты и CI зелёные.

- Кандидаты в PR upstream: регистрация `generate_recurring_posts`, права `post_delete`, `RATELIMIT_ENABLE` в `production.py`, порты 5432/8000 в compose, `APP_DOMAIN` для Caddy.
- Lock-файл (`uv pip compile`) и Dependabot: `requirements.txt:60-64` описывает инцидент из-за их отсутствия. Выровнять Python 3.12/3.13.
- Django 5.2 LTS: 5.1 без security-патчей, но ранний апгрейд увеличит расхождение с upstream. Делать после первого успешного цикла merge, с полным прогоном тестов.
- Не удалять выключенные приложения (intelligence, oauth_server): они отключены настройками, удаление кода создаст конфликты.

## Чего не будет
- Intelligence (ИИ-подсказки, Stripe): закрытый облачный сервис авторов, в self-hosted недоступен принципиально.
- White-label по пространствам: заявлен в README, в коде не реализован; брендинг делать одной правкой `templates/base.html` и токенов `theme/static_src/src/styles.css` при реальной потребности.
- Heroku/Render/Railway: единственная цель деплоя — Docker Compose на VPS.
- Русификация интерфейса: по решению владельца UI остаётся на английском.

## Риски плана
- Проверки Meta/TikTok/Google: недели, несколько раундов, требования к документам и видео; начинать в первый день.
- География: без доступа к API Meta с сервера и к кабинетам с вашей стороны три сети из пяти недостижимы.
- Единственный мейнтейнер upstream (94 % коммитов): форк должен быть самодостаточным (CI, lock-файл, маленькие коммиты).
- AGPL-3.0 при сетевом использовании клиентами.
- Bot API Telegram не идемпотентен: таймауты при больших видео дают дубли, поэтому timeout у провайдера обязателен.
