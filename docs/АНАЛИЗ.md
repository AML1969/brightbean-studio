# BrightBean Studio: анализ проекта

Дата анализа: 27.10.2026. Состояние upstream: `brightbeanxyz/brightbean-studio`, коммит `1d11c52` (PR #226).
Метод: восемь независимых агентов разобрали по подсистеме, читая код; риски уровня high
дополнительно проверялись отдельным агентом-скептиком. Всё, что ниже, подтверждено ссылками на файлы.

## 1. Что это за проект

Self-hosted платформа для планирования, согласования и публикации контента в соцсети.
Монолит на Django 5.1 (~61 тыс. строк Python без тестов и миграций, 24 апп-модуля),
серверный рендеринг шаблонов + HTMX + Alpine.js + Tailwind 4, PostgreSQL, фоновый воркер
на django-background-tasks с собственной обёрткой, REST API на django-ninja и MCP-сервер
для ИИ-агентов, OAuth 2.1 сервер для Claude Desktop.

| Факт | Значение |
|---|---|
| История | 655 коммитов, март–октябрь 2026 |
| Авторство | 94,5 % коммитов одного человека (Jan Schmitz), один CODEOWNER |
| Доля ИИ-ассистированных коммитов | 236 коммитов с трейлером Co-Authored-By: Claude, 42 из 66 merge-коммитов из веток `claude/` |
| Тесты | 2737 тестов, 46 тыс. строк, проходят за ~110 с на PostgreSQL 16; отношение тестов к коду 0,76 |
| CI | ruff, mypy, pytest + makemigrations --check, Docker build, gitleaks; actions закреплены по SHA |
| Лицензия | AGPL-3.0 |

Вывод по зрелости: проект молодой, но с необычно высокой инженерной дисциплиной в ядре
(движок публикации, провайдеры, API). Слабые места сосредоточены во «внешнем кольце»:
операционная конфигурация, фронтенд, авторизация отдельных view, отсутствие локализации.

## 2. Архитектура по подсистемам

### 2.1 Мультитенантность и доступ (`apps/accounts`, `organizations`, `workspaces`, `members`)
- Пользователь → Организация (роли owner/admin/member) → Рабочее пространство (owner/manager/editor/contributor/client/viewer).
- При регистрации сигнал автоматически создаёт «My Organization» и «My Workspace».
- Центральный шлюз изоляции: `RBACMiddleware.process_view` (`apps/members/middleware.py:86-106`) отвергает любой `/workspace/<uuid>/` без членства.
- Три режима регистрации: open / invite / closed, валидируются при старте.
- Приглашения с лимитами, блокировками строк и защитой от гонок. Хорошо покрыто тестами.
- Дизайн явно «v1: одна организация на пользователя», но код создаёт мульти-членство (принятие приглашения существующим пользователем), а middleware берёт `.first()` без сортировки. Это подтверждённый риск для сценария агентства.

### 2.2 Публикация (`apps/composer`, `publisher`, `calendar`, `approvals`, `client_portal`, `media_library`)
- Модель: `Post` с дочерними `PlatformPost` на каждый аккаунт; статус поста выводится из детей.
- Согласование: draft → pending_review → approved → pending_client → scheduled; клиентский портал по magic-link.
- Движок публикации (`apps/publisher/engine.py`) очень аккуратен к двойной публикации: SELECT FOR UPDATE, идемпотентный ключ, ретраи 60/300/1800 с, sweep зависших публикаций каждые 60 с, подтверждение асинхронных (TikTok).
- Медиа: валидация по magic-bytes, лимиты 20 МБ фото / 1 ГБ видео, ffmpeg для превью, квоты хранилища.
- Сильная сторона всего проекта. 155 тестов на движок, 210 на композер.

### 2.3 Провайдеры соцсетей (`providers/`, `apps/social_accounts`, `apps/credentials`)
13 провайдеров через единый ABC `SocialProvider` с флагами возможностей.

- **Telegram и VK отсутствуют полностью.**
- Токены и ключи приложений шифруются AES-256-GCM, ключ выводится из `SECRET_KEY` + `ENCRYPTION_KEY_SALT`. Версионирования ключа нет: смена любого из них делает все токены нечитаемыми.
- Добавление платформы на практике (замер по DEV.to): ~15 исходных файлов и 2–3 миграции, а не «один файл + реестр», как утверждает `development_specs/architecture.md`.

### 2.4 Аналитика, inbox, уведомления (`apps/analytics`, `inbox`, `notifications`)
- Часовой cron собирает метрики аккаунтов и постов в таблицы снимков; лестница частоты по возрасту поста; общий «предохранитель» квот.
- Inbox опрашивается каждые 5 минут + вебхуки Meta/YouTube; серверная проверка окон ответа в DM Meta (24 ч / 7 дней / human agent).
- Уведомления: единая точка `notify()`, дайджесты, тихие часы, RFC 8058 отписка, бюджет исходящей почты в БД.
- Подтверждённая проблема роста данных: снимки метрик постов никогда не очищаются, а сырой JSON провайдера дублируется в каждую строку метрики.

### 2.5 API для агентов (`apps/api`, `mcp`, `oauth_server`, `api_keys`, `intelligence`)
- REST `/api/v1/` и MCP `/api/v1/mcp` с 19 инструментами используют один сервисный слой; есть тест паритета.
- Ключи `bb_studio_…` хешируются HMAC, права ключа пересекаются с живыми правами выдавшего.
- Многоуровневые rate-limit, идемпотентность, аудит.
- **Intelligence** (ИИ-подсказки, биллинг Stripe) — тонкий клиент к закрытому облачному сервису авторов. Включается только при пяти переменных, выдаваемых вендором. В self-hosted версии недоступен, время на него не закладываем.

### 2.6 Фронтенд (`templates/`, `theme/`, `static/`)
- 249 шаблонов, ~24 тыс. строк; Alpine-состояние инлайном; `compose.html` — 3030 строк, из них ~1000 JS.
- **Локализация отсутствует**: ни одного `gettext` в Python, 11 тегов `trans` в двух шаблонах, нет LocaleMiddleware. Русификация — это проход по ~250 шаблонам и 90 вызовам `messages.*`.
- White-label заявлен в README, но не реализован: «Brightbean» захардкожен в 68 шаблонах, цвета рабочего пространства используются только для точек в календаре.
- Внешние скрипты (flatpickr, chart.js, sortablejs) грузятся с cdn.jsdelivr.net без SRI.
- Доступность слабая: нет `role="dialog"`, фокус-ловушек, у аватаров нет alt.

### 2.7 Инфраструктура и конфигурация (`config/`, Docker, compose, CI)
- Настройки разделены base / development / production / test, валидация ключевых переменных при старте.
- Воркер `run_studio_worker`: две полосы, одна зарезервирована под публикацию; корректная обработка SIGTERM.
- Пять целей деплоя: compose dev, compose prod + Caddy, Heroku, Render, Railway.
- SQLite реально работает для локального запуска, но тесты требуют PostgreSQL.

## 3. Подтверждённые риски (отсортированы по важности для self-hosting)

### Критично до выхода в интернет
1. **PostgreSQL с паролем `postgres` опубликован на `0.0.0.0:5432` в production-compose** (`docker-compose.yml:44`, prod-override порт не убирает). На VPS база будет открыта миру.
2. **Rate limiting молча отключается, если в `.env` остался `DEBUG=true`** (`config/settings/base.py:664` вычисляет `RATELIMIT_ENABLE = not DEBUG` до того, как `production.py` переопределит DEBUG). `.env.example` поставляется с `DEBUG=true`.
3. **Без `REDIS_URL` все лимиты, антибрутфорс и кэш отзыва API-ключей живут в памяти каждого процесса** (`base.py:137-158`); prod-compose запускает 4 воркера gunicorn, лимиты фактически ×4.
4. **Нет `.dockerignore`**: `COPY . .` запекает `.env` с секретами, `.venv`, `media/` и `.git` в образ (`Dockerfile:21`). Исправлено в этом репозитории.
5. **`docker-compose.prod.yml` хардкодит `DATABASE_URL` для migrate, а app/worker читают из `.env`**: совет README «поставьте сильный пароль» ломает стек.
6. **`APP_DOMAIN` не передаётся в контейнер Caddy**, он всегда обслуживает `localhost` (`Caddyfile:1`, `docker-compose.prod.yml:49-53`).
7. **SMTP по умолчанию `localhost:587`**: на свежей установке любое приглашение или сброс пароля падает с исключением.

### Авторизация внутри рабочего пространства
8. **Любой участник пространства может удалить любой пост, включая опубликованные** (`apps/composer/views.py:2498`, только `@login_required` и проверка членства).
9. **Эндпоинт смены статуса платформенного поста позволяет любому участнику выставить `published`/`draft`/`failed` чужому посту** (`apps/composer/views.py:1294`).
10. Действия `schedule`/`add_to_queue` в композере и CSV-импорт обходят режим согласования и право `publish_directly` (только `publish_now` его проверяет).
11. Любой участник, включая client/viewer, может переименовать пространство и сменить иконку (`apps/workspaces/views.py:107`).
12. `request.org` берётся `.first()` без сортировки при возможном мульти-членстве (`apps/members/middleware.py:53`).

### Операционные
13. Снимки аналитики не чистятся, сырой JSON дублируется на каждую метрику (`apps/analytics/tasks.py:944`); таблица растёт без ограничений.
14. Повторяющиеся посты (RecurrenceRule) никогда не генерируются: `generate_recurring_posts` нигде не зарегистрирован (`apps/calendar/tasks.py:33`).
15. Шифрование без версии ключа: ротация `SECRET_KEY` или `ENCRYPTION_KEY_SALT` ломает все сохранённые токены.
16. Django 5.1 вышел из security-поддержки с релизом 6.0 (декабрь 2025); зависимости без lock-файла.
17. Ошибки throttling Meta (HTTP 400 с кодами 4/17/32/613) не распознаются как rate limit, только HTTP 429.
18. Facebook/Instagram через FB Login не получают refresh-токен; при сбое продления аккаунт застревает в TOKEN_EXPIRING.
19. Inbox без пагинации: доступны только последние 50 сообщений.
20. Инлайн-скрипт в HTMX-партиале медиатеки несёт nonce ответа, а не документа, и блокируется строгим CSP в production (`templates/media_library/_tag_input.html:48`).

## 4. Технический долг, влияющий на доработки
- Два параллельных пути создания/перевода постов: `save_post` в views (ручной) и `composer.services` (для REST/MCP); проверки уже разошлись.
- `apps/composer/views.py` 4292 строки: композер, канбан идей, CSV, RSS, Unsplash в одном модуле.
- django-background-tasks не поддерживается; проект несёт свою обёртку. Makefile `worker` запускал устаревший `process_tasks` без выделенной полосы публикации (исправлено в этом репозитории).
- Нет lock-файла, дрейф версий Python (3.13 в `.python-version`, 3.12 в Dockerfile и CI), pre-commit отстаёт от CI.
- `settings_manager` в основном каркас: из 41 ключа настроек читается 1–2; UI настроек нет.
- 15 МБ скриншотов ревью в `output/` и устаревший `development_specs/architecture.md` (описывает DRF, которого нет).
- Покрытие тестами неровное: нулевое у `workspaces` и `settings_manager`, у `media_library` views затронуты 3 из 17 URL.

## 5. Что подтверждено запуском
- Нативный запуск на Python 3.13 + PostgreSQL 16: миграции, Tailwind, суперпользователь, вход, принятие Terms, рабочее пространство с календарём.
- `pytest`: 2736 passed, 1 skipped за 111 с. `makemigrations --check`: чисто. `ruff`, `mypy`: чисто.
- Docker-путь в среде анализа проверить не удалось (нет демона), он опирается на README и чтение compose-файлов.

## 6. Выводы для нашей доработки
1. Ядро брать как есть, не переписывать: движок публикации и провайдеры в хорошем состоянии.
2. Перед выходом в интернет закрыть пункты 1–7 раздела 3; это полдня работы.
3. Для приоритетных сетей владельца (TikTok, YouTube, Instagram, Facebook) провайдеры есть и покрыты тестами; критический путь — не код, а developer-приложения и их review.
4. Telegram придётся писать: провайдер через Bot API для каналов, по образцу `providers/mastodon.py` плюс форма подключения как у Bluesky/DEV.to; затронет ~15 файлов и 2–3 миграции.
5. Русификация интерфейса — отдельный крупный этап (gettext по ~250 шаблонам), её стоит делать после стабилизации, иначе каждый merge из upstream будет конфликтовать.
